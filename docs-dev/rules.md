### 規則 1：版號只有一個來源——`VERSION`（V5.0.0 起）

升版 = 改根目錄 `VERSION` 一行（例如 `5.1.0`），其他全部由 `hooks.py` 在 build 時產生：

| 出現位置 | 怎麼來的 |
|---|---|
| header 站名旁、footer 右下徽章 | 模板 `overrides/` 讀 `config.extra.version` |
| 三份獨立教材的版號徽章 | hook 在 build 時注入整合層（頂部列＋footer），原始檔不含版號 |
| `extra.css` / `extra.js` 的 `?v=` cache-busting | hook 自動加，`mkdocs.yml` 不寫版號（坑 #78）|
| ZIP 檔名 `CCM Manual V?.?.?.zip` | 手動，要跟 `VERSION` 一致 |

> 🔴 **不要再在任何檔案寫當前版號**（README、CLAUDE.md、extra.js、extra.css 都不寫）。頁面的「最後更新」由 git 日期自動產生（V5.4.0），文件資訊表不再寫最後更新。
> **例外**：`docs/drug-lookup/` 是另一個 SELA 專案的複本，保留它自己的版號。

### 規則 6：唯一閘門＝`mkdocs build --strict`（V5.0.0 起）

所有守門檢查都併進 `hooks.py`，違規一律 `log.warning`，`--strict` 直接 Aborted。**本機和 CI 跑的是同一條指令**，Git Pusher 推上去後 GitHub Actions 擋得住，不再靠交付者記得跑腳本（內審 A-2）。

```bash
rm -rf site && mkdocs build --strict 2>&1 | grep -E "WARNING|ERROR|Aborted|Documentation built"
# 期待：只有 "Documentation built in X seconds"
```

`hooks.py` 在 build 中執行的檢查：

| 檢查 | 原本 | 現在 |
|---|---|---|
| 同檔 anchor、nav、缺檔 | 第 1 道 | mkdocs 本身（需 `validation.links.anchors: warn`）|
| 跨檔 anchor | 第 2 道 `check_anchors.py` | V5.3.0 起 hook 的 `check_site_links()` 掃 site/ 每個站內 href（含 raw HTML、教材、模板、404 頁），目標檔與 anchor 都要存在；`check_anchors.py` 刪除 |
| markdown 連結指向非文件路徑 | 報 INFO 被忽略 | `unrecognized_links: warn`（V5.3.0）|
| 教材整合層、教材版號 | 第 3 道 `integrate_teaching.py --check` | V5.3.0 起整合層由 hook 注入，工具刪除；drug-lookup 比對 sha256 |
| 文件元資料 | 第 4 道 `check_doc_meta.py` | V5.4.0 起「最後更新」改用 git 日期（`git-revision-date-localized`）；hook 檢查 front matter 的審閱欄位、`review_due` 過期即 WARNING；`check_doc_meta.py` 與 manifest 刪除 |
| UI JS 執行期 | 第 5 道 `check_js_runtime.py` | **刪除**：JS 不再注入任何東西，沒有東西可壞 |
| 每頁要有分類 | `check_js_runtime.py` 涵蓋率 | hook：頁面沒有合法 category → WARNING |
| 規則 8、規則 11 | 手動 grep | hook |

> **build 需要 git 歷史**（CI 用 `fetch-depth: 0`）。在沒有 `.git` 的目錄預覽：`CCM_GIT_DATES=false mkdocs build --strict`。

!!! danger "🔴 第 1 道能生效的前提：`mkdocs.yml` 要有 `validation` 設定"
    ```yaml

        anchors: warn              # 死 anchor → WARNING → --strict 直接 fail
    ```

### 規則 12：標題層級設計語言

**先決條件（內容編排）**：分層之前先確認內容編排合理——**同類的東西放一起、有邏輯順序**（時間／重要性／工作流程）。內容亂排再怎麼分層都救不回來。**編排穩定後才動層級**。如果分層時發現「同類東西散在文件四處」，回去整理內容順序，再來分層。

**層級用途**：

| 層級 | 用途 | 內容份量門檻 | 是否上 TOC |
|------|------|----------|----------|
| **H1** | 檔名／頁面標題（每檔唯一）| — | — |
| **H2** | 頁面內主要分區（5–10 個為宜，最多 12 個）| — | ✓ 必上 |
| **H3** | H2 之下的子章節 | **≥ 20 行** | ✓ 必上 |
| 邊緣 | 結構性章節但內容偏短 | 15–19 行 | 看狀況（傾向 H3）|
| **H4** | 細層或內容短到 TOC 上不需要獨立列 | **< 15 行** | ✗（toc_depth=3 蓋住，可改用粗體段落）|

**設計原則**：

1. **TOC 是「快速到附近」、不是「精準到小點」**——錨點之間距離太近、使用者點過去一頁就看到兩三個錨點，TOC 反而難掃描。內容短的子段直接用 H4 或粗體段落，不要塞進 TOC
2. **內容份量決定層級**：用「< 15 行 / 15–19 行 / ≥ 20 行」三段分。邊緣段（15–19 行）原則上升 H3，但若是「情感段落」「結尾話」「重複別處的簡介」這類非結構性內容，降 H4
3. **不再使用 H2 的「## 目錄」區塊**——Material 右側自動 TOC 已提供同樣導航，自寫「## 目錄」H2 會跟自動 TOC 視覺重複（且自寫的不會自動更新）
4. **作者主動判斷 H3 vs H4**：規則告訴你閾值，但作者要自己看「這段內容值不值得 TOC 獨立導航」。寧可少不要多

**寫作時自我檢查**：

- 一個檔的 H2 數量超過 12 個 → 多半是「層級壓平」（把子章節寫成 H2 並列）
- 完全沒 H3 → 同組 H2 該收成「一個 H2 + 多個 H3」
- 大量 H4 → 內容寫得細，但確認 H4 不依賴 TOC 導航是否 OK
- TOC 條目（H2+H3 加總）超過 ~30 項 → 太細，回頭看哪些 H3 該降 H4

**坑 #31（V3.4.7+）盤點**：V3.4.6 後 17 份 MD 中違反規則 12 的有三檔——`A_work-guide`（40 H2，模式 1：層級壓平，**V3.4.7 已修**）、`C3-C6_other-cancers`（12 H2、0 H3，模式 2：完全沒 H3，**V3.4.8 已修**）、`G_quality-index`（22 H2、11 H3，**5 個 H1**，模式 4：多 H1 + H3 偏少，**V3.4.8 已修**）。F 檔（6 H2、18 H3、40 H4）原本被誤列為「模式 3 違規」，V3.4.8 重新評估：F 檔 TOC（6+18=24 項）已合理，H4 多是內容性質（如十三癌別影像關鍵詞、137 種藥物分類），**不需上 TOC**——符合規則 12 設計原則「TOC 是快速到附近、不是精準到小點」。**F 檔不算違反規則 12**。

**A_work-guide 修法已決議（V3.4.7 候選）**：保守版方案——5 H2（4 部分 + 附錄）+ 28 H3（≥ 20 行的 20 個 + 邊緣 8 個全升）+ 7 個 < 15 行的子段降 H4。砍 `## 目錄` H2。預期 TOC 33 項（vs. 現在 104 項）。**動手前**：先確認內容編排合理（規則 12 先決條件），有發現「同類東西散在四處」就先重整內容、不要急著降層級。

### 規則 13：拆檔與巢狀門檻

何時用單檔平鋪 vs 拆多檔巢狀的決策依據：

| 情境 | 處理 |
|------|------|
| **單檔 < 500 行** | 平鋪頂層（TOC 處理頁內導航夠用）|
| **單檔 500–1000 行** | 邊緣，看內容性質決定 |
| **單檔 > 1000 行** | 拆檔 + 巢狀（單檔太長，TOC 滑不完）|
| **頁面數 = 1** | 平鋪頂層（沒得巢）|
| **頁面數 2–3** | 看單檔長度決定 |
| **頁面數 ≥ 4** | 巢狀（避免 nav 太散）|

**規則 15 新增（時效性內容處理）**：

V3.4.26 EGFR 補助專案啟示「明確截止日」+ V3.4.27 五癌篩檢「每年改版」啟示「年度推廣物」——兩種不同時效性內容該訂統一處理規則：

**規則 15 條文**：所有具時效性的內容（外部資源、補助、推廣、政策、**臨床準則版本**、給付規定等）都需在文件中明確標示時效類型，並提示讀者**驗證時點**。避免文件因時間流逝而誤導使用者。

**第 4 類「準則版本」的三條特則**（V4.3.0 從 AJCC 8 vs 9 事件訂出）：

1. **標到版本，不要只寫系統名**——「AJCC 第 8 版」而非「TNM 分期」。沒標版本 = 讀者無法判斷是否過期
2. **設單一權威源對照表**（規則 14）——版本狀態集中在一處（本專案：[C0 分期系統版本對照表](docs/C0_general.md)），各檔 cross-ref 過去。**改版本只改一處**
3. **不默默升版**——準則改版是**臨床/法規決定，不是文件決定**。新準則出現時：標示落差 + 指出誰能確認（醫師 / 病理科 / 癌登窗口），**不要自己把舊表改寫成新版**

> **為什麼第 3 條最重要**：準則改版改的是「判讀語言本身」。文件搶先升版 → 個管師照新版填癌登、但癌登系統還在收舊版編碼 → 資料錯。**準則版本的採用時點是機構決定的。**
